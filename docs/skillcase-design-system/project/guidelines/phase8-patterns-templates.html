0What phase 8 must resolve

The system has 88 components and one template. That ratio is the current bottleneck: a designer starting a new screen has every part and no shape. Five templates were evidenced across phases 1–5, but building five independently would repeat the A1/A2 fork at the template layer — which is exactly the defect D-007 records. So the question is not "build the five", it is how few templates explain the evidence.

The answer below is three, plus the one that already exists.

Why "task screen" absorbs the results screens. Earlier phases counted workspace and results as two templates because they feel different. Structurally they are the same: back-bar, a well, a footer action. What changes is the body pattern — question versus answer review — and the body is a pattern slot, not a template. Making them one template is what stops the eighth results screen from forking.

Why the lesson screen stays separate. It is the one case where the difference is not the body but the context: a different page surface, a different ink (D-024b), a different footer grammar (two buttons, gold primary). Forcing it into "task screen" would either flatten the Guided German identity or bloat the task template with a mode flag that changes everything. Two templates is the honest count.

A1/A2 recorded explicitly

A1 and A2 module select are one configuration of the select screen, differing only in module_number handling — and A2 ignores it (defects.md P2). The two near-identical production implementations should conceptually be one template. Production code is not merged by this document; the design system expresses one template and the fork is recorded as debt (D-007).

3What phase 8 should build, in order

  1. The announcement pattern first. Busy and error states are silent across AppButton busy, SkeletonList and StateMessage (defects.md P3, and the phase-7 accessibility gap). Its shape depends on how a screen composes them — which is exactly what a template decides. Building it inside the first template, rather than before or after, is the only way to get it right once.
  2. Task screen. Highest leverage: it explains 14+ audited surfaces, and it is where the timer, block progress and review patterns land.
  3. Select screen. Second: 10+ surfaces, and it retires the A1/A2 fork at the design layer.
  4. Lesson screen. Last of the three, because Guided German is the most fully audited surface and least at risk of drifting while it waits.

Not in phase 8: the Maya consolidation (needs a product decision, not a template), the payment step (two surfaces with genuinely different semantics — wait for a third), and the scholarship urgency port (open question 7).

5Readiness

ALMOST — ready for screen production in the three audited systems only

Guided German, the B1 exam system and the job pipeline are audited deeply enough that a new screen in them can be generated from this system with confidence. Profile, content and scholarship are mapped but not traced to state level.

ASSUMPTION: that the three templates above cover surfaces in the unaudited areas — untested, and the first Profile screen will test it.

6A note on method

Phase 7 closed with a self-inflicted defect worth carrying forward: a colour was declared absent from the codebase on the strength of a hex grep, in a Tailwind codebase where most colours never appear as hex. Nine files were changed on that one bad premise before the user caught it (D-024, withdrawn).

The rule this establishes for phase 8: evidence is a resolved class name or a read file, never the absence of a string. And no sweep wider than the evidence that justified it.
