UX QA report — run 1

The first pass of the UX QA persona across every screen the design system currently holds: five screen kits and four templates. Eleven UX checks and four system checks. Findings only — nothing here was fixed in this pass, by design.

Date 27 Aug 2026Scope 5 kits · 4 templates · ~40 screensFindings 12P1 3

1The headline

The design system's screen kits are less accessible than the product they reproduce.

Production carries aria-label on its modals, nav, lesson back button, pronunciation controls and loading skeletons — StreakLeaderboardModal, UsageLimitModal, TrialEndedModal, NewNavbar, ProgressBar, GrammarScreen, ExerciseLayoutSkeleton and a dozen more. Across all five kits in ui_kits/ there is not one.

This is the single most important finding of the run, because it inverts the usual assumption. The kits were built to be faithful to production; on labelling they were faithless in the wrong direction, and every screen generated from them would inherit the loss. It is our defect, not the app's.

3Findings

QA-001 — No accessible name on any icon-only control, in any kit

P1Class Design-system debtOwner UI CreationCheck Semantic HTML / ARIA

Back, close, mute, play and Listen buttons render an SVG and nothing else. A screen reader announces "button". Production labels most of these; the kits label none. Affects all five kits.

QA-002 — Modal built from div onClick, bypassing AppModal

P1Class Design-system debtOwner UI CreationCheck Keyboard navigation

mobile-app/HomeScreen.jsx:84 — the streak leaderboard backdrop is a clickable <div>. No role="dialog", no Escape handler, no focus trap, no return of focus on close. It cannot be dismissed by keyboard at all. AppModal exists and handles every one of these. Production's own StreakLeaderboardModal is better than this reproduction.

QA-003 — Focus ring not applied below the component layer

P1Class Design-system debtOwner UI CreationCheck Focus visibility

Phase 7 put --ui-focus-ring on AppButton, AppTabBar, ListRow, ChapterRow and TextField. Kit-local controls — AmberCta, GhostCta, Cta, HomeScreen's continue button, every icon button — have no focus treatment at all, so keyboard users lose their place the moment they leave a DS component. This is the kit-layer half of the production defect already recorded in defects.md.

QA-004 — Icon controls at 28×28, against a 44px system minimum

P2Class Product / design decisionOwner PM + StewardCheck Target size

HomeScreen back and close, premium-flow back, exam-flow Listen: all 28px. --ui-target-min is 44px. The kits are correct — they reproduce production geometry faithfully. So this is not a kit defect; it is an unresolved conflict between the system rule and the shipped app, and it needs a decision rather than a fix. Options: enlarge the hit area without changing the visual box (invisible padding, the usual answer), change the token, or scope the token to new surfaces only.

QA-005 — Four local CTA components duplicating AppButton

P2Class Design-system debtOwner StewardCheck Component adherence

AmberCta and GhostCta (premium-flow), Cta with a navy/amber variant (job-flow), and an inline gradient button (HomeScreen). All four reimplement what AppButton already does, and each carries its own hardcoded gradient — which is how a palette drifts. Exactly the pattern the Steward persona exists to stop.

QA-006 — Raw hex in three kits while a semantic layer exists

P2Class Design-system debtOwner UI CreationCheck Token adherence

#002856, #5b6472, #fcd34d, #fde68a literal throughout job-flow, premium-flow and mobile-app. exam-flow proves the alternative works: it is written entirely in var(--ui-*). Mechanical to retrofit, and it is what makes the dark theme reachable for these surfaces.

QA-007 — No kit renders an error or validation state

P2Class State completenessOwner PMCheck Error / validation messaging

Across ~40 screens: no failed upload, no rejected form field, no network error, no payment decline. The job pipeline has six document uploads and not one shows a rejection. The system has error primitives; no screen exercises them. Until a brief enumerates these states, the system's error handling is theoretical.

QA-008 — 10px text in the exam timer

P2Class Product / design decisionOwner PMCheck Text sizing

ExamScreens.jsx:203 — the HH/MM/SS unit labels are 10px. Reproduces production. It is the smallest type in the product, on the most time-pressured screen in the product. The value beneath it is 20px and legible, which mitigates but does not resolve it.

QA-009 — 11px labels are the default for form and meta text

P3Class Documentation issueOwner StewardCheck Text sizing

Field labels, back-bar text and eyebrow captions sit at 11px across job-flow and lesson-flow, matching production. Legible, but the type scale does not currently say whether 11px is a sanctioned floor or an accident. Document the floor either way.

QA-010 — Screen titles as div in some kits, h2 in others

P3Class Design-system debtOwner UI CreationCheck Semantic HTML

job-flow uses real <h2> for every screen title. mobile-app and premium-flow use styled <div>. No screen in any kit has a document-level <h1>, so the heading outline starts at level 2 or does not exist.

QA-011 — Kit-level transitions do not check reduced motion

P3Class Design-system debtOwner UI CreationCheck Motion

ScoreRing, MetricBar and AppButton's busy state all honour prefers-reduced-motion (verified in phase 7). Transitions written inline in the kits — progress-bar width, sheet slide-up — do not. Low impact: the durations are short and none loop.

QA-012 — ✕ as a close glyph

P3Class Design-system debtOwner UI CreationCheck Semantic HTML

HomeScreen.jsx:88 uses the literal character. Screen readers read it as "multiplication x" or skip it. Every other close control in the system is an SVG. One-character fix, listed for completeness.

4What passed

  • Semantic buttons. Real <button type="button"> almost everywhere an action exists — the modal backdrop (QA-002) is the exception, not the rule.
  • Disabled vs locked is genuinely distinguished. Onboarding's Next uses the real disabled attribute with a grey treatment; locked premium content uses the paywall pattern with an explanation and a route forward. Two different meanings, two different treatments, no conflation. This was a system rule defined in phase 7 and the kits already honour it.
  • Loading and busy states exist and are distinct — skeletons for page load, in-button spinners for submit.
  • Contrast on the primary surfaces. Navy on white, ink on gold, white on navy all clear AA. The three known AA failures are measured, staged and awaiting your decision — unchanged by this run.
  • The templates are clean. All four use tokens, DS components and the focus ring. The pipeline's output layer is in better shape than its historical input.

5What could not be checked

Three of the eleven checks cannot be completed by reading markup, and are recorded as not run rather than passed:

  • Screen-reader traversal. Needs NVDA or VoiceOver on a real device. This is the reason accessibility maturity is capped at 5/10 and will stay capped.
  • Real keyboard traversal order. Tab order can be reasoned about statically; it cannot be verified statically.
  • Touch accuracy on device. 28px is a measurement; whether it is a problem for the actual user population is a device test.

8Recommended next action

One backfill pass over the three oldest kits — labelling, focus, tokens — before any new screen is built. QA-001, 003 and 006 are the same retrofit touching the same lines, and they are mechanical. Doing them now costs one pass; doing them after the next surface is built costs two, and every screen produced in between inherits the gap.

QA-004 and QA-008 wait for you: they change how the shipped app looks, so they are not the pipeline's to decide.
