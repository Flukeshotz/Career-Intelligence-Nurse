Exam system — behavioural audit

Traced from SkillCase-Frontend-main. The headline finding is structural: the product does not have an exam system, it has three of them, mounted on separate route trees, with separate data shapes, separate scoring rules and separate result surfaces. They are not variants of one flow. Any design work that treats "the exam screen" as a single thing will be designing for whichever of the three happened to be in front of it.

0Five findings that change the design work

1. Three exam systems, not one. /b1/exams/* is the four-section Goethe/TELC paper flow. /exam/:testId is a scheduled single-test flow with teacher marking. /scholarship is a standalone funnel reusing the shell with exam-only chrome. They share a vocabulary ("exam", "score", "review answers") and almost nothing else.

2. Passing means three different numbers. The generic exam sets passed = score >= 60. The B1 congratulations screen bands at 75/50. Per-question correctness on writing and speaking is qScore >= 50. Nothing in the codebase reconciles them, and no screen states a pass mark to the learner at all.

3. Two of the four B1 results screens do not use the shared ScoreRing. Writing and Speaking import it. Reading and Listening hand-roll a 120px ring with the stroke hardcoded to #0BAA45 — green at every score. A learner scoring 12% on Reading sees a green ring; the same 12% on Writing is red.

4. The timer survives reload, and that is deliberate. Each section writes an expiry timestamp to localStorage keyed b1_exam_timer_{userId}_{paperId}_{section}, so refreshing does not buy more time. But there is no exit guard anywhere — no beforeunload, no confirmation — so the Back button silently abandons an in-progress timed section while its clock keeps running.

5. Completion is a server 403, not a client state. Re-entering a finished paper throws 403 { alreadyCompleted }, which three separate screens catch and translate into a redirect to Congratulations. The "already done" case is therefore an error path in the code. It has no loading treatment of its own, and any screen that forgets the catch shows a failure message for a successful outcome.

Section status is the whole model

Every navigation decision in the B1 flow reads from one map: sections[].status ∈ not_started | in_progress | completed, plus a submission-level status. There is no partial-section resume state in the UI — a section is open or finished. The dashboard derives "all four complete" client-side by checking the four literals, and the results screens re-derive the same fact independently to decide whether Back goes to the dashboard or to Congratulations.

not_started→in_progress→completed⇢submission.completed⇢reset → not_started ×4

The scoring kit is validated, with one correction. ScoreRing, MetricBar and AudioPlayer reproduce production correctly and their bands prop was the right call — the exam audit found three more scales, which a hardcoded scale would have made unreproducible. The correction is to scoreBands.js: it documents three scales and there are seven. Rules 4–7 are now recorded there too. No default changed.

What the scoring kit does not need

No new scoring component is justified by this audit. The exam results screens want a ring, bars and a player, and those exist. The 2×2 section scorecard on Congratulations is a single-use layout of four coloured boxes; the correct/incorrect/skipped tally appears twice, in Reading and Listening only. Neither clears the bar. The gap is a decision, not a component: until someone rules on the pass mark, any "pass" affordance the system ships would be inventing product behaviour.

Considered and deliberately not extracted

  • Section tile (the 190px block-selector card). One occurrence. A layout, not a component.
  • Correct / incorrect / skipped tally. Two occurrences, Reading and Listening — the auto-marked sections. Writing and Speaking cannot have one. Extracting it now would imply it belongs to results screens generally, which is false.
  • Answer-review option row. Present in both the B1 and generic systems, but structurally different: B1 has a fixed lettered A–Z model over six question types; the generic exam has fourteen types including image options, ordering, matching pairs, sentence correction, and a teacher-pending state with no verdict at all. Extracting either shape would freeze a difference nobody has decided about. Needs a product ruling first
  • Score band scale. A foundation decision, already data in scoreBands.js. Not UI.

GNext

The remaining unaudited surfaces are A1/A2 practice modules, profile and content browsing, and the scholarship funnel. None is behaviourally complex in the way the exam system is; breadth-first is defensible for the practice modules, whose chapter templates were already partly read in phase 1. The scholarship funnel needs audit-first treatment — it has its own shell chrome, which means its own navigation model.

Defects found in this pass are recorded in guidelines/defects.md together with the four from phases 1 and 2. Nothing in this audit was fixed in the codebase; that is not this project's job.
