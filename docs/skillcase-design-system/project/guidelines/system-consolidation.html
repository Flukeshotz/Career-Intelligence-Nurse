2Finding A — the A1/A2 module screens are one template, accidentally forked

Evidence
pages/a1/ and pages/a2/ are structural mirrors: flashcard, grammar, listening, reading, speaking, test — each with a Select and a Content screen. All ten Select screens render from ChapterSelectTemplate. But there are two copies of that template: components/a1/ChapterSelectTemplate.jsx (191 lines) and components/a2/ChapterSelectTemplate.jsx (185 lines).

I compared them line by line. They are near-identical. The only differences:

DifferenceA1A2Classification
Level headingHard-coded A1Hard-coded A2Accidental should be a prop
Chapter numberingchapter.module_number || index+1index+1 onlyBehavioural drift A2 mislabels chapters when the server's numbering is sparse
Tour anchor idA1-chapter-lista2-chapter-listAccidental casing inconsistency
Everything elseIdentical — 140 px header image, the 30 px level heading, the 50 px-wide chapter progress carousel, the #019035/#edb843 fill logic, the badge styles, the six-row skeleton loaderSame

Classification: accidental inconsistency, not intentional product behaviour. The A2 copy is a fork of the A1 file that then drifted. The evidence is that the drift is asymmetric and non-semantic — nobody deliberately decides that A2 should number chapters differently from A1.

The design system already covers this. ModuleTopBar, LevelHero, ChapterStrip and ChapterRow were ported from the A1 template in an earlier pass. All ten Select screens are therefore already representable — they need a level prop, not new design.

Recommendation

Add level to LevelHero (it currently hard-codes its heading, mirroring the source's flaw) and document the module-select pattern as one template with a level parameter. Report the A2 chapter-numbering divergence to engineering as an implementation bug — do not encode it in the design system. A design system that faithfully reproduces a copy-paste bug has documented an accident as a rule.

3Finding B — the exam flow is two patterns, not ten screens

Evidence
pages/b1/exams/ holds twelve files: ExamSelect, PaperSelect, ExamBlockSelector, ExamCongratulations, and then a strict {Skill}Workspace + {Skill}Results pair for Reading, Writing, Listening and Speaking. The results screens import shared parts from a different feature: ScoreRing, MetricBar, AudioPlayer and OcrModal all come from pages/b1/describe-speak/components/, plus components/b1/UmlautKeyboard.

So the exam surface decomposes as:

LayerCountWhat varies
Selection chrome3Exam type → paper → block. Almost certainly one list pattern, three data sources.
Workspace pattern4 instancesReading and Listening are question-answering; Writing adds the umlaut keyboard and OCR; Speaking adds recording. Shared spine, four input modes.
Results pattern4 instancesAll four build on ScoreRing + MetricBar. Writing and Speaking add AI feedback; Reading and Listening are objectively marked.
Terminal1Congratulations.

Critically, ScoreRing and MetricBar are already shared between Describe & Speak and the exams in production. That is not accidental duplication — it is the product's own evidence that a scoring pattern exists and is reused. It is the single strongest candidate for a design-system pattern in the un-audited territory.

Recommendation

Treat the exam surface as audit-first per §24 — the behavioural model is substantial, and I have not yet traced timing, autosave, submission, or how a part-finished paper resumes. But design it as two parameterised patterns plus a scoring kit, not ten screens. Extracting ScoreRing, MetricBar and AudioPlayer first would serve the exams, Describe & Speak, and Speaking practice simultaneously.

5System-level gaps this exposes

Reported as gaps per §22, not built.

Gap 1 — no loading, empty or error primitives

Requirement: every list surface in the product has a skeleton loader; ChapterSelectTemplate ships a six-row pulsing skeleton, and the lesson flow has bare "Loading Lesson…" text and an error branch including a 409 "not available yet" case. Existing: nothing. The system has 86 components and not one loading, empty or error state. Why insufficient: these are the most-repeated states in the product and the least designed. Recommendation: extract three primitives before adding any new surface — they will be needed by all ~11 remaining ones. Systemic? Yes. Confidence: high.

Gap 2 — the scoring kit is a pattern the system doesn't have

Requirement: ScoreRing + MetricBar + AudioPlayer, already shared across exams and Describe & Speak in production. Existing: nothing comparable. Recommendation: extract as a pattern. This is the clearest evidence-backed componentisation opportunity in the codebase — reuse is already proven, so §15's bar is met. Systemic? Yes. Confidence: high.

Gap 3 — LevelHero inherits a hard-coded level

Requirement: one heading component serving A1, A2, B1, B2. Existing: LevelHero, which reproduces the source's hard-coded string. Recommendation: parameterise. Systemic? Yes. Confidence: high. Reversibility: easy.

Gap 4 — the product tour is invisible to the system

Requirement: tourSteps.js, A1ProductTour, A2ProductTour, B1ProductTour and the lesson flow's TapGuideOverlay attach spotlights to anchor ids across many screens. Existing: nothing; and the Guided German audit already flagged the intro spotlight as undrawn. Why it matters: a tour overlay is a cross-cutting state on screens the system claims to have covered — every "represented" screen has an undocumented second state. Recommendation: one overlay primitive plus a documented anchor-id convention. Systemic? Yes. Confidence: medium — I have not read the tour engine.

7Self-evaluation against the audited flows

§38 requires validating the system against known-good cases rather than generating more components. Run against Guided German, the one complete audit.

QuestionAnswer
Did the system reproduce existing UI accurately?Mostly. 15 screens match. Two known errors were caught and fixed only when checked against a real screenshot (the job welcome screen) — meaning fidelity was assumed, not verified, on surfaces without screenshots.
Did it preserve intentional differences?Yes — three separate verdict surfaces were kept distinct rather than merged into one component with a colour prop.
Did it miss states?Yes, systematically. The audit found the kit draws end states and omits opening states: disabled CTAs, audio-playing, drag-in-progress, committed turns. The bias is toward the screenshot-worthy state.
Did it create unnecessary variants?No evidence of it. But LevelHero shows the opposite failure — reproducing a source flaw instead of parameterising.
Did it correctly identify reusable patterns?Partly. The lesson primitives were extracted well. The scoring kit — reused in production — was missed entirely until this pass.

The lesson for the remaining work: the system's weakness is not coverage, it is state completeness and verified fidelity. Adding eleven more surfaces at the current standard would multiply that debt. Extracting the three missing state primitives first is the higher-value move.

8Recommended sequence — for approval

  1. Extract the state primitives — loading skeleton, empty state, error state. Needed by every remaining surface. Small, high leverage.
  2. Extract the scoring kit — ScoreRing, MetricBar, AudioPlayer. Proven reuse; unblocks exams, Describe & Speak and Speaking practice at once.
  3. Parameterise LevelHero and document the module-select template. Closes 10 surfaces cheaply.
  4. Audit the exam flow properly — workspace behaviour, timing, autosave, resume, submission. Then design two patterns.
  5. Backfill the missing states in Guided German from the audit's gap list.
  6. Then breadth-first on profile and the content surfaces, looking for the one content-list pattern.
