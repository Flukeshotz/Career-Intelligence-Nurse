Guided German — behavioural flow audit

Traced from SkillCase-Frontend-main, not from the design kit. The controller is src/pages/learnGerman/lesson/NewLessonFlow.jsx (1,744 lines); it walks a server-supplied screens[] array and each entry's type selects one of twelve layouts. Nothing below is inferred from the kit's static screens.

Route /learn-german/lesson/:chapterIdScreen types 12User-facing states 41Audit date 26 Aug 2026

0Five findings that change the design work

1. There is no fill_blank screen type. Fill-in-the-blank ships as a quiz whose question carries the gap and whose image is omitted. It is multiple choice, never a text input — there is no keyboard, no free-text validation, no input field anywhere in the lesson flow. Designing a typed-input blank would invent an interaction the product does not have.

2. Incorrect is not "correct in red". Three different verdict surfaces exist, and they disagree on purpose. QuizResultModal reveals the right answer on correct and withholds it on incorrect. DragResultModal renders only the modal that applies and its correct headline is "Excellent!", not "Correct!". conversation has no modal at all — the verdict is inline on the option row.

3. The conversation is self-advancing. No Check button, no CTA. Tapping a correct reply auto-advances after 1,000 ms; tapping a wrong one shakes the row and clears the selection after 600 ms. A correct answer locks the row set against further taps.

4. outro never renders as its own step in the normal path. handleNext intercepts it: when the next screen is an outro, the level-complete modal opens over the current screen and the outro layout is skipped. It only renders when it is the current screen after a back-navigation.

5. Progress excludes intro and scenario. Both are removed from the denominator and hide the progress bar entirely (showProgressBar). The kit currently draws a progress bar on both.

AComplete lesson flow, as the code runs it

The sequence is data-driven — the server supplies the array — but the controller imposes hard structure on top of it. This is the canonical shape, with the controller's rules named.

Entry → GET lesson config → branch on user_status
  • completed + not review mode → level-complete modal immediately, flow never starts
  • in_progress with 0 < user_screens_completed < total → resume at that index, all prior marked answered
  • otherwise → index 0
intro → scenario (×n) → vocab (×n) → grammar (×n) → quiz / listen_choose / match_following / match_image / unjumble (interleaved, ×n) → conversation_intro → conversation (×n, contiguous block) → [outro intercepted] → Level Complete modal → /learn-german with autoStartNext

Back navigation is not symmetric with forward. resolvePrevIndex skips every scenario on the way back but keeps intro reachable, and from any conversation turn it rewinds past the whole contiguous conversation block rather than one turn. Returning forward from conversation_intro then jumps straight back to the turn you left, via conversationResumeIndex.

Solved work is remembered across back-navigation. hydrateStateForScreen restores from three maps: solvedOptionSelections (quiz, listen_choose, conversation), solvedMatchFollowingMap (matched pair ids), solvedDragScreensMap (placed items + slot statuses, and it re-enters the correct drag state). A revisited solved screen is not blank — the design must cover a pre-filled revisit state.

BScreen-by-screen behavioural map

1 · intro — level / chapter opening

Implemented in screens/IntroScreen.jsx. This is the answer to "intro to level/chapter" — there is no separate level-intro screen type.

What the user sees
The scene photo full-bleed (falls back to a hard-coded Cloudinary bakery image when screen.image is absent), and one bg-black/50 card, max-width 300 px, holding: screen.level ("Level 1") at 16 px white/90, the lesson title at 24 px bold (from lessonData.title, not the screen), Maya's bubble, Maya at 168 px, and Continue. No description field and no progress information — the progress bar is suppressed here.
Entry condition
Screen index 0 of a fresh or non-resumed lesson.
Interaction
Continue only. Tapping the page does nothing on intro (unlike scenario/outro).
Typing / audio
MayaDialogueBubble typewrites the line and simultaneously speaks it via useMayaTTS, firing a light haptic per character. A mute/replay waveform button sits at the bubble's top-right corner.
CTA
"Continue" + arrow, amber gradient, #eec139 border. Always enabled — it does not wait for the typewriter.
After CTA
handleNext → next index. Maya and the bubble travel to the next screen as shared layout elements (layoutId="mayaMascot", "dialogBubble", "lessonBg") — 550 ms on the image, 450 ms on the bubble.
Guided-tour state
When getLgGuideStage() === CHAPTER_CLICK_DONE, a spotlight overlay (TapGuideOverlay) appears over the Continue button 1 s after the dialogue finishes. This is a distinct visual state the kit does not have.
Kit status
Partial Layout is right; the kit draws a progress bar that the app hides, and has no tour-spotlight state.

2 · scenario — the situation

screens/LessonScenarioScreen.jsx. Several may run back to back.

What the user sees
Photo filling the upper area (rounded 16, shadow); beneath it a bg-black/5 well, min-height 140 px, with an inner shadow. Maya sits at left:-8px; bottom:0, 110 px wide, overflowing the well. Her bubble is inset 95 px from the left with a rotated-square tail. Continue below.
Entry / progress
Follows intro. Progress bar hidden and excluded from the denominator.
Dialogue queue
screen.dialogues[], advanced by dialogueIndex. Tapping anywhere on the screen advances it (the root div carries the handler) — as does Continue. Falls back to "..." if the array is empty.
Skip?
No skip. The user must step through every line, but there is no wait — advancing mid-typewriter is allowed, so tapping fast is the de-facto skip.
CTA
"Continue". Always enabled. On the last line it leaves the screen; before that it advances the queue.
Ends
Last line + Continue → onGuidedCompleteTap → handleNext.
Kit status
Partial Built, but only the first queue position, and again with a progress bar the app suppresses.

5 · quiz — multiple choice (incl. fill-in-the-blank)

screens/QuizScreen.jsx. Multiple choice only. Options are screen.options[], lettered A–D by a LETTERS constant that supports a maximum of four.

initial→option_selected→checked: correct|checked: incorrect→retry (same screen)
Two data variants
With image: photo at h-48/h-52 above the question. Without image (screen.image absent, or present but failed — imgError): the block is simply not rendered and the question rises to the top of the sheet. This second variant is how fill-in-the-blank ships, so the photo cannot give the answer away.
Question
Rendered as text and spoken: a 40 px waveform button beside it plays question through Polly, with the same sonar-ring + handtap idle treatment.
Option states
Unselected: white, zinc-200 border, grey letter well. Selected: bg-blue-100, #1E76F3 border, blue-200 letter well, blue-600 label. Only one selected state — no per-option correct/incorrect colouring on this screen type. The verdict lives entirely in the modal.
CTA
"Check" + arrow. Disabled (grey bg-gray-200) while selectedOption === null; amber gradient once any option is picked. "Prev" takes 2/5 width when canGoPrev.
Validation
handleCheckQuiz: correctOptionIndexes.includes(sel) when the array exists, else sel === correctOptionIndex. Sets quizState to correct or incorrect; medium haptic on correct, heavy on incorrect.
Retry
Unlimited. Dismissing the incorrect modal returns to the question with the wrong option still selected — the learner changes it and checks again. No penalty, no attempt counter, no effect on progress.
Kit status
Represented Both variants and both verdicts are now drawn. The disabled-Check initial state is not.

6 · listen_choose — hear & answer

screens/ListenAndChooseScreen.jsx. Same validation path as quiz; different affordances.

audio_unplayed→audio_playing→option_selected→correct|incorrect|skipped
Sees
"Tap to listen" at 16 px black/50 above a 52 px rounded-2xl waveform button. No image, ever. The question sits below the player, then A–D options.
Audio
Plays screen.audioText, not the question text. Replayable any number of times; guarded by if (!isSpeaking) so taps during playback are ignored rather than restarting.
Option states
Selected is a lighter treatment than quiz: bg-blue-600/5 with #1E76F3 outline and a rounded (not rounded-lg) letter well.
Escape hatch
"Can't listen now" — a slate-300 text button above the CTA row. It calls onSkip, which logs question_skipped with reason_code: "cannot_listen_now", records the answer as incorrect for analytics (listen_choose_skipped), and advances. The learner is not shown a verdict and is not blocked.
CTA
"Check", disabled until an option is picked. Audio need not have been played.
Kit status
Represented Missing the playing state and the skip's silent-advance path.

7 · match_following — two columns

Interaction
Tap-to-pair, not drag. Tapping one side sets selectedLeft/selectedRight; tapping the other resolves immediately against leftItem.matchId. There is no Check step — each pair is judged on the second tap.
Correct pair
Medium haptic, id pushed to matchedPairs, recentMatch set for a 600 ms celebration, then cleared. Matched rows are locked out of further taps.
Incorrect pair
Heavy haptic, wrongPair set for 600 ms (shake + rose), selection cleared, and nothing is remembered — the learner simply tries again. No modal, no counter.
CTA
"Next". handleNext hard-returns while matchedPairs.length < leftItems.length, so the button is inert until every pair is solved.
Kit status
Partial All four row states are drawn on one static screen; the 600 ms transient nature of wrongPair/recentMatch is not expressed, and the kit implies a Check step that does not exist.

8 · match_image — drag onto the picture

empty→dragging→placed→checked: correct (locked)|checked: incorrect
Interaction
dnd-kit. Bank → slot places into the hovered slot specifically. Slot → slot always swaps (the displaced word returns to the source slot). Dropping outside a slot returns a placed word to the bank; a bank word released in open space auto-places into the first empty slot. Tapping a bank word does the same.
Correct-slot lock
Three separate guards refuse to move a word out of, or into, a slot already confirmed correct. Partial credit is durable.
Check
checkDragQuiz stamps every slot correct/incorrect/null and sets dragQuizState. Unplaced slots count as wrong.
Verdict
DragResultModal — green headline is "Excellent!", CTA "Continue"; incorrect is "Incorrect!" with screen.incorrectFeedback and "Try again". Only the applicable modal mounts.
Kit status
Partial One placed row is drawn. The drag overlay (white pill, blue outline, 1.05 scale), the hovered-slot tint, the swap and the correct-lock are absent — as is DragResultModal itself, which the kit substitutes with the quiz modal.

9 · unjumble — jumbled words

screens/UnjumbleScreen.jsx, 471 lines, its own self-contained dnd-kit context and its own verdict state. The existing interaction is sound; it should not be redesigned.

Available words
screen.items[] in a centred wrapping bank, min-height 52 px. A word already in the sentence is replaced in the bank by a greyed placeholder at 50% opacity that holds its slot — the bank never reflows.
Placing
Tap appends to the sentence's next position; drag can drop anywhere outside the bank and also appends. Both refuse once sentenceItems.length === slots.length.
Ordering
Placed chips are useSortable — dragging one over another reorders live via arrayMove with a horizontal strategy. The sentence wraps across underlined rows computed by a width-estimating algorithm (label.length * 8 + 56, clamped 72–170 px) against a ResizeObserver.
Removing
Tap a placed chip, or drag it back to the bank zone (which tints bg-blue-50/60 on hover). Either action clears every slot status — the whole answer returns to unjudged.
Chip states
Placed: white, zinc-300 outline. Correct: emerald-100/50, green-700 outline and text, plus a 14 px green tick. Incorrect: rose-200/40, red-500 outline and text, plus a red cross. Bank chips are smaller (py-2 vs py-1.5) and never coloured.
CTA
"Check", disabled until all slots are filled. Grades each position against matchId, so the learner sees exactly which words are misplaced — then DragResultModal opens on top.
Retry
Modal → "Try again" → idle. The per-chip green/red marks stay visible, so the learner corrects only what is wrong. Interaction is frozen while the modal is up (if (dragQuizState !== "idle") return).
Kit status
Partial The graded state is drawn. Missing: bank placeholders, the drag overlay, the bank-hover tint, and DragResultModal.

10 · conversation_intro — character handover

Sees
Maya top-left at 88 px with a 210 px bubble; below, the scene rises with rounded top corners. Once Maya finishes, the character's bubble fades in at bottom:55%, inset left:40%. A 176 px mix-blend-multiply gradient darkens the base so the buttons read.
Dialogue
screen.dialogues[], else screen.mayaDialogue. Advanced by tapping the bubble — only after the current line has finished typing (if (!currentDialogueFinished) return).
CTA lock
This is the one screen with a genuinely gated CTA. Mid-queue it reads "Continue" and needs currentDialogueFinished; on the last line it becomes "Start Conversation" and needs characterDialogueFinished — i.e. Jacob's line must finish typing too. Disabled styling: bg-zinc-200, text-zinc-400, cursor-not-allowed, and the arrow greys with it.
After CTA
Normally the next index. But if the user had reached a conversation turn and come back, conversationResumeIndex sends them straight to that turn instead of restarting the block.
Kit status
Partial Final unlocked state is drawn; the disabled state — the more common one — is not.

11 · conversation — the roleplay

screens/ConversationScreen.jsx. Each turn is its own screen in the array; the transcript is reconstructed, not stored. This is the most under-represented screen in the kit.

turn_open→reply_correct (1s, auto-advance)|reply_wrong (600ms, self-clears)→turn_committed→completed_fallback
Who speaks
The character (characterDialogue, optional englishMeaning) in an #E4EFFF bubble on the left with a 32 px white→orange-300 gradient avatar; the learner on the right in white. Page background #D4E5FF, no sheet, header floats over it with a 65 px + safe-area inset.
History
conversationHistory walks backwards from the current index while type === "conversation" and stops at the first non-conversation screen. Past turns replay the learner's actual pick from conversationSelections, falling back to the lowest correct index.
Audio
Auto-speaks the current turn's line on mount unless muted — the only screen that speaks without a tap. Every bubble carries its own waveform button; the three-way handler is genuinely tri-state: muted → unmute and play; playing this bubble → mute and stop; otherwise → play. Mute is a global preference (ttsMutePreference) shared across bubbles and screens.
Answering
Options sit in a 75%-wide white card headed by screen.question ("Select the correct reply"). No Check button and no CTA. Correct tap: emerald fill, green outline, CheckCircle2, 1.02 scale, medium haptic, then onNext(idx) after 1,000 ms. Wrong tap: rose fill, red outline, XCircle, a 5-px shake keyframe, heavy haptic, and the selection self-clears after 600 ms. Once a correct answer is registered the whole set is locked.
Correctness
getCorrectIndexSet accepts correctOptionIndexes[] or legacy correctOptionIndex, and defaults to {0} when neither is present.
Committed turn
Once conversationSelections[index] exists the option card is replaced by the learner's reply as a plain past bubble.
End of block
If the final turn is the last screen, or the next is an outro, showConversationCompletedFallback renders a "Completed" amber button (plus Prev) inline in the transcript, which goes to /learn-german.
Kit status
Needs design The kit draws one open turn with a generic selected row. Missing: the correct/wrong inline verdicts, the committed turn, the avatar, per-bubble audio and its three states, the English meaning line, and the Completed fallback.

DLevel complete

Trigger
handleNext when the next screen is an outro or the array is exhausted. Sets levelComplete and calls persistComplete — which is idempotent, guarded by a promise ref.
Headline
"Level Complete!" at 24 px, then Maya's line from getCompletionDialogue(lessonData, screen), typewritten, in a bubble with a two-layer CSS triangle tail. Maya sits in two concentric discs (240 px white/40, 160 px white) and springs up with bounce: 0.4.
Statistics
A yellow-200→orange-400 card with a outline-4 outline-yellow-50 inset ring. Three possible rows: Coins (+coinsAwarded from the server, bar 80%), Days Streak (+1, bar 92%), German words learnt (+vocabCount, bar 75%). Bars are decorative fixed widths, not real percentages.
Streak behaviour
streakUpdated is true only when this is the first lesson completed today. When false the streak row is omitted entirely — the card renders with two rows and the words row inherits the earlier animation delay. This is a real second layout, not a greyed row.
Icon bubbles
28 px white discs with a 2 px orange-300 border, animating left: 0% → barWidth over 1.1 s and poking out of the track (overflow-visible). Haptics fire progressively as each bar fills — light below 34%, medium to 67%, then heavy.
Word count
Number of vocab screens; falls back to grammar screens, then to lessonData.vocab_words.length, then to 4. Four sample words are cached to sessionStorage for the home screen's recap animation.
CTA
"Start next lesson", navy pill. Goes to /learn-german with autoStartNext: true, so the home hub plays its recap animation and auto-starts the next lesson. The ✕ merely closes the modal, leaving the learner on the lesson's last screen.
Side effects
Coins added to the Redux user; lgLessonComplete and skillcase:coins-updated window events fire so the navbar ring and tab bar refetch.
Kit status
Partial Built with all three rows. The no-streak two-row variant is not drawn, and the streak icon is a stand-in (the app loads it from Cloudinary, so it is not in public/).

FGaps to design, in priority order

  1. Conversation turn states — correct, wrong-with-shake, and committed. Five of six states are undrawn and this is the lesson's climax.
  2. DragResultModal, both states. A second verdict component with its own copy ("Excellent!" / "Continue"), currently misrepresented by the quiz modal.
  3. Disabled CTA states — quiz, listen_choose, unjumble and conversation_intro all open disabled. Today the kit only shows the enabled end state.
  4. Audio playing state — one change to AudioTapButton (rings and handtap gone, waveform animating) that corrects six screens at once.
  5. Level complete without a streak — the genuine two-row card.
  6. Drag mechanics — drag overlay, hovered-slot tint, bank placeholder, correct-slot lock.
  7. Solved-screen revisit — pre-filled quiz, matched pairs, locked drag placements.
  8. LeaveLessonModal, plus loading, error and the 409 "not available yet" screens.
  9. Progress-bar suppression on intro/scenario — a correction, not an addition.

Two behavioural questions I cannot answer from the code alone: whether a completed lesson re-entered from the hub should land on the level-complete modal (current behaviour) or on a reviewable transcript; and whether isReviewMode deserves its own visible chrome, since it currently suppresses analytics and completion but looks identical to a first run.
