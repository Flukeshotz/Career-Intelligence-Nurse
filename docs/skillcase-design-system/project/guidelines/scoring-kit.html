Scoring kit

Phase 2, same order as phase 1: evidence → extract → validate → document. Three components shipped — and the pass turned up something more consequential than the components themselves. The reusable parts were never the problem; the score scale underneath them is forked four ways, and one results screen renders two of those scales at the same time.

1Evidence — reuse was already proven

Unlike the state primitives, this kit did not need inference. Production already shares these three across two features: the exam results screens import them from pages/b1/describe-speak/components/, a sibling feature's folder. That import path is itself the evidence — someone reached across a feature boundary rather than copy-paste, which is the strongest signal a design system can get.

2The finding — four score scales

Both shared components colour themselves by score band. Tracing where those bands come from produced this:

70 / 40describe-speak scoreUtils.js — the shared one
75 / 50Exam results screens' local helpers
70 / 50Every greeting, including scoreUtils' own
3Different mid-tone colours for one band

Scale 1 — the shared definition

// describe-speak/utils/scoreUtils.js
getScoreColor(score)        >= 70 green · >= 40 orange/amber · else red
getScoreStrokeColor(score)  >= 70 #16A34A · >= 40 #F59E0B · else #EF4444
getScoreGreeting(score)     >= 70 "Good job" · >= 50 "Well done!" · else "Keep practicing!"

Note the internal inconsistency already present here: colour bands at 40, greeting bands at 50. A score of 45 is coloured as mid-tier but greeted as bottom-tier by the same utility file.

Scale 2 — the exam fork

// ExamWritingResults.jsx (and ExamSpeakingResults.jsx, identically)
getMetricColor(val)      >= 75 bg-green-600 · >= 50 bg-amber-300 · else bg-red-500
getMetricTextColor(val)  >= 75 text-green-700 · >= 50 text-orange-500 · else text-red-500

These screens define their own helpers locally — while importing MetricBar, which uses scale 1. They also hand-roll their own score ring (size = 120, strokeWidth = 10, circumference maths duplicated inline) alongside importing ScoreRing.

The visible consequence. On a single exam results screen today:

  • A score of 72 renders green in the imported MetricBar and amber in the surrounding chrome.
  • A score of 45 renders amber in MetricBar and red in the chrome.

Two contradictory verdicts on the same number, in the same viewport. The scoring kit card demonstrates this side by side.

I have not resolved the 75/50 question. Whether a pass is 40, 50 or 75 is a product decision about assessment, not a styling choice, and picking one to make the system tidy would be exactly the failure the operating model warns against.

4Extract — what shipped, and the one structural choice

The scale is extracted as data in scoreBands.js, not baked into the components:

SCORE_BANDS.canonical   { good: 70, mid: 40 }   // describe-speak, the shared one
SCORE_BANDS.examMetric  { good: 75, mid: 50 }   // the exam fork, recorded verbatim
SCORE_BANDS.greeting    { good: 70, mid: 50 }   // greetings everywhere

Every component takes bands, defaulting to canonical. This is the whole point of the pass: any screen can be reproduced faithfully today, and when the product decides on one scale, the change is one object rather than six files.

ComponentVariantsFaithful to
ScoreRingAny size; 160/12 default, 120/10 for the exam geometry#D4D4D8 track, -90° rotation, 500ms ease-out, 8px caption clamped to 80px
MetricBarworkspace 12px on zinc-300 · compact 6px on zinc-200Both variants' exact weights, line-heights and the 42/31px radii
AudioPlayerworkspace white card · review transparent48px slate button, amber fill in both, 75ms track transition

Rejected this pass: a ScoreSummary composite wrapping ring + bars (the four results screens arrange them differently enough that a composite would need to expose everything it encapsulated); a ScoreBadge (the difficulty badges in ExamWritingResults use the same palette for a different semantic — difficulty, not score — and conflating them would be a category error); and a greeting component (one line of text is not a component).

5Validate

SurfaceReproducible with the kit?
Describe & Speak workspace + successYes — this is the source; ring at 160, bars at both variants, player in both forms.
Exam writing / speaking resultsYes, including the divergence — pass bands={SCORE_BANDS.examMetric} for the chrome and leave MetricBar on canonical to reproduce today's screen exactly, or set both to one scale to preview the fix.
Exam reading / listening resultsPartly — these are objectively marked and use greetings plus per-question review, which I have not yet traced. The ring and bars apply; the review list does not exist yet.
Guided GermanNo, correctly — the lesson flow has no scores. LevelCompleteCard's stat bars look superficially similar but are decorative fixed widths (80% / 92% / 75%), not score-driven. Unifying them would encode a false relationship.

The Guided German negative repeats phase 1's lesson and is worth stating plainly: two things that look alike are not the same component when one is data-driven and the other is ornament.

7Escalations now open

Three defects found across phases 1 and 2. All are engineering/product calls, not design-system changes, and none has been silently normalised.

Defect 1 is the one worth acting on soon — it is not cosmetic. A learner shown amber for a 72 on one row and green for the same 72 on another has been given two different verdicts on their own work.

8Next

Phase 3 is the exam audit, and phase 2 has sharpened what it needs to answer: the four workspaces' input modes, timing and autosave, submission and resume, the per-question review lists on the results screens, and whether the 75/50 threshold is policy or accident. The scoring kit means that audit can now focus on behaviour rather than re-deriving visual structure.
